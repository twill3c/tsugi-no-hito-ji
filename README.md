# 次の一字(tsugi-no-hito-ji)

青空文庫で組んだ**文字言語モデル**の中身を、最後まで見せるアプリ。
大規模言語モデルの「出口」——次の一トークンの確率分布と、そこからどう選ぶか——を、
手元で動く小さなモデルの上で全部開けてみせる。

**本番** <https://tsugi-no-hito-ji.vercel.app>

外部への通信はゼロ。API 鍵も課金もいらない。モデルの中身は青空文庫の本文そのもので、
確率はブラウザがその場で数えている。

---

## 遊び方

### 予測盤 —— 次の一字をどう見積もっているか

書き出しを入れると、次に来る一字の確率が棒で出る。
「親譲りの無鉄砲で」と入れれば「小」が 87%(『坊っちゃん』を読んでいるので覚えている)。
「こころ」なら「が」「で」「を」が並ぶ。

つまみは 4 つ。

| つまみ | 何をするか | 動かすとどうなるか |
|---|---|---|
| **温度 T** | 確率を `p^(1/T)` に置き換えて正規化する | 下げると尖って堅くなる。上げると溶けて珍しい字が出る |
| **top-k** | 上位 k 字だけ残す | 小さくすると「無難な字しか出ない」 |
| **top-p** | 累積が p に届くまで残す | 分布が尖っているときは 1〜2 字、平らなときは数百字残る |
| **文脈の上限 L** | 何文字さかのぼるか | 0 にすると字の出現頻度だけになる |

**「どの長さの文脈が効いているか」の帯**が、このアプリの見どころ。
モデルは長さ 0 から長さ L まで全部混ぜていて、帯はその配分そのものである。
よくある並びなら長い文脈が濃く効き、珍しい並びなら短い文脈に譲る。
表の「出現 n」は本文を実際に数えた回数で、飾りではない。

たねを固定してあるので、同じたね・同じつまみなら何度やっても一字も違わない。

### 文脈の山 —— 長ければいいわけではない

「いまの本で測る」を押すと、文脈の長さを 0 から 8 まで変えながら、
**学習にも調整にも使っていない別の作品**を何ビットで言い当てられるかを測る。

谷は 2〜3 文字のあたりにある。そこから先は**伸ばすほど当たらなくなる**。
40 万字の中で 8 文字の並びが一致することはほとんど無く、
一致したとしても 1 回か 2 回で、その次に来た字が今回も来るとは限らないからである。

下の図は、同じ本の**先頭 N 字だけ**を読ませたモデルを N を変えて並べたもの。
読んだ量が増えると曲線全体が下がり、**谷が右へ動く**。
効く文脈の長さは、読んだ量が決めている。

### かなあて勝負 —— 人間 対 モデル

シャノンが 1951 年に英文でやった実験の日本語版。
伏せた一字を、当たるまで何度でも言う。同じ問題をモデルにも解かせて、
**何回目で当たったか**の分布から両者のビット数を挟む。

人間には**上界しか出ない**。下界の式は「確率の高い順に当てにいく」ことを前提にしていて、
人間の推測順はそうならないからである(上界のほうは、推測回数の列から本文を復元できる、
というだけで出るので誰にでも使える)。

## 中身

```
build/      前処理・参照実装・較正・測定・検品
  prepare.py    青空文庫から採録し、本文と接尾辞配列を焼く
  model.py      参照実装(Python)。テストが照合に使う
  calibrate.py  割引 D を dev 本文の上だけで選ぶ
  measure.py    held 本文で報告値を測る
  scaling.py    「読んだ量 × 文脈長」の曲線束を焼く
  hygiene.py    原稿の文字種検査
  js_dump.mjs   出荷実装の出力を JSON に落とす(二実装照合の相手)
  page_check.mjs 実ブラウザ検品
web/        出荷物(静的ファイルのみ)
  js/model.js   出荷実装。build/model.py とは別々に書いてある
  js/shannon.js 推測回数からビット数を挟む
  data/         本文・接尾辞配列・事前計算値
tests/      pytest 42 件
```

### 動かす

```bash
python build/prepare.py      # 採録(要 ../aozora-sakuin/data)
python build/calibrate.py    # 割引 D の選定(dev 本文)
python build/measure.py      # 報告値(held 本文)
python build/scaling.py      # 読んだ量 × 文脈長
python -m pytest -q          # 42 件
npm install && node build/page_check.mjs   # 実ブラウザ検品
```

### 確率の作り方

長さ 0 から L まで、絶対割引で下から混ぜ上げる。

```
p_0(c) = (N_c + 1) / (N + V + 1)
p_m(c) = max(k_m(c) - D, 0) / n_m + γ_m · p_{m-1}(c),   γ_m = D · u_m / n_m
```

見た回数から D を引き、引いた分をまとめて短い文脈に譲る。
1 回しか出ていない文脈は 20 分の 19 を譲る —— つまり、ほとんど信じない。
D = 0.95 は **dev 本文の上だけ**で選んだ(報告用の本文で選ぶと較正が循環する)。

### 数え方は 3 通りある

同じ「出現回数」を、走査して作る表・接尾辞配列の範囲なめ・二分探索だけ、の
3 通りで数えている。3 つが一致することをテストで確かめ、
絶対値は 18 字の本文の手勘定と総当たりで固定してある。

## 測って捨てたもの

最初の目玉は「**文脈は長いほど当たる**」だった。混ぜ方を 2 通り、割引を 11 通り、
コーパスを 4 つ試して、どの組み合わせでも 4 文字を超えると悪化した。
**主張のほうを捨てて**、代わりに成り立った「谷の位置は読んだ量で決まる」を目玉にした。

かなあて勝負では、人間の下界が上界を上回った(6.02 bit と 3.42 bit)。
定理の前提を人間が満たしていなかった。人間には上界だけを出すことにした。

どちらも `HARNESS_CHANGELOG.md`(HC-001 / HC-003)に経緯が残してある。
